# 写作口径

> 目标读者是**要照着做的前端/后端开发**。写「要重实现成什么样」，不是「遗留代码长什么样」。

## 1. 总则

- **以功能行为为主**。类名、行号、SWT 控件 API、`I*Service` 方法名**只作溯源线索**，不构成设计；不清楚就写「行为」而不是「实现」。
- **三者一致**（迁移动机的落点）：**控件元素一致**（遗留的输入项 / 勾选项 / 下拉 / 按钮 / 表格列 / 页签，新页面都要有对应元素，可重组、不可无故缺失）、**功能布局一致**（查询区 / 分类树 / 结果列表 / 多 Tab 弹窗 / 子弹窗的分区与信息架构一致）、**业务逻辑一致**（默认值、显隐禁用、字段联动、校验、编码生成、保存/删除/调价流程一致）。
- **不照搬实现**：遗留与新技术栈 / 控件模型不同，实现方式不照抄；重实现遵循仓库项目规范与组件库（`@/base/ui`，antd v4 定制版，非官方 `antd`）。
- **可执行**：每条描述都应能落到「字段 + 控件 + 校验 + 触发 + 结果」。
- **可核对**：涉及遗留行为处标注来源（`<遗留>/ui.<mod>.<layer>/.../XxxEditor.java`、`messages.properties`），便于复核。
- **不复制字节**：遗留中文（GBK）必须转码或重录为 UTF-8。
- **单一维护**：共享内容只写一处，其余引用。
- **不确定就标记**：`<!-- TODO：待源码复核 -->`，并在 `_进度台账.md` 登记，**不要编造**。

## 2. 各类内容怎么写

**字段表**（控件顺序）——顺序即界面顺序，从左到右 / 从上到下：

| # | 字段 | 控件 | 码表 | 必填 | 规则 / 校验 |
| --- | --- | --- | --- | --- | --- |
| 1 | <字段名> | 下拉 | <码表编码> | ✔ | 不允许重复 |

- 控件用**通用名**（文本 / 下拉 / 勾选 / 数字 / 日期 / 弹窗选择），对应的具体组件在分册「线框与布局要点」/「实现要点」里说。
- 码表填**码表编码**（遗留码表的编码值，如大写短码），无则 `—`。
- 规则写**可判定的约束**（`> 0`、不允许重复、长度、联动来源）。

**事件表**：

| 触发 | 行为 |
| --- | --- |
| 添加 / 更新 | 新增或修改一条记录（校验唯一、数量 > 0） |

- 用「**新增 / 编辑界面差异**」专门说明：入口、默认值、可编辑性、页签显示范围（注意：**新增态弹窗通常只显示主页签**，不能据此推断页签不存在）。

**UI 交互**：分「默认值 / 显隐与禁用 / 联动 / 校验」四类写；联动要写清**谁触发谁、赋什么值、是否实时**。

**线框与布局要点**（放在分册「功能布局」节末尾）：**线框**（ASCII，表达层级与比例、标注区域 / 分区 / 页签，参照 `images/` 截图，符号见 `00-前端布局规范.md` §2；不追求像素）+ **布局要点**（分区顺序、栅格密度、相对位置、组件选型）：

```text
┌─ 查询区 ────────────────────────────┐
│ [名称]         [状态▾]  [查询][重置] │
├─ 左树 ─────┬─ 结果列表 ─────────────┤
│ 分类        │                        │
└─────────────┴────────────────────────┘
```

- **栅格密度**：通用密度（每行 3~4 对、`GridFormAntd` 列轨、成组与对齐）按 `00-前端布局规范.md` §3.4 **引用，不复述**；分册只写本册特有的密度差异（如某页签固定 4 对）。
- **列表列顺序与表单归属**：按 `00-前端布局规范.md` §5（序号后紧跟操作列、删除用危险样式）；**字段表单写在弹窗分册、列表分册不展开**（新增 / 编辑共用一个弹窗，按入参区分）。

**实现要点（末节）**：只说**本册特有**的做法（组件选型、复用策略、前后端双重约束、本册特有参数 / 接口形态等）；通用做法统一指向 `00-前端布局规范.md`（骨架/栅格见 §3，通用实现清单见 §3.5），避免重复。

## 3. 术语与前后一致

- 同一实体在全文用同一名词（如「<字段 / 实体名>」），首次出现可括注遗留英文名。
- 状态/枚举写**取值**（'Y'/'N'、`defunct_ind`），不写「启用/停用」这类模糊词而不给字段。
- 跨模块通用约定（逻辑删除、审计字段、院区归属、编码、SQL 平移）写在根 `README.md`「迁移通用约定」；模块**特有**约定（如码表）写本模块 `00-总览与通用约定.md`；分册只引用。

## 4. 篇幅与颗粒度

- 单册 **60–200 行**为宜（硬顶由 `scripts/audit-docs.sh --max-lines` 控制，默认 450 行，超出即警告）；超过说明该拆册（页签多 → 拆页签册）。
- 表格为主、散文为辅；避免大段复制遗留代码。
- 截图只作视觉参考；**文字与截图冲突时以源码为准**，并在册内说明差异。实现前先核对截图与文档，**发现不一致时停止写代码，先补充修订文档再继续**。

## 5. 一册一个家（反冗余）

> 一条**解释性内容**只应有一个「家」，其它地方**链接**过去；短小、自洽的**规则**允许重述。

- **一个事实一个家**：同一句解释 / 清单 / 表格出现在 2 册以上即为冗余 → 保留最贴近该事实的那一册，其余改为一句话 + 链接。
- **不写变更史**：不写「原先 / 现在 / 已不再 / 曾叫 / 已改名 / 从 X 移到 Y」；只写**当前状态**，历史交给提交记录与台账。
- **不写进度标注**：正文 / 线框里不写「已实现 / 待实现 / future」——状态以代码与索引为准（`_进度台账.md` 除外）。
- **不复述权威来源**：后端接口清单、码表、字段结构以来源为准，不在多册各自复述成列表。
- **不写推导过程**：不写实现推导、测试走查、被否决的方案；只留结论与理由。
- **保留例外（重要）**：安全 / 约束类的**短规则**（一两句）允许各册自洽重述；**解释与清单必须单一来源**。
- **自查**：`scripts/audit-docs.sh --dup-strict`（跨册重复长句）、`--max-lines`（单册篇幅预算）。

## 6. 反例（禁止）

- ❌ 大段粘贴遗留 Java / SWT 代码或 GBK 中文。
- ❌ 写「参照原系统逻辑」而不写具体行为。
- ❌ 把共用页签在多册各写一遍。
- ❌ 用「应该/大概/可能」描述规则；不确定请标 TODO。
- ❌ 索引/导航/册号未同步。
